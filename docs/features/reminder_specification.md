# リマインダ機能 仕様書

- 対象アプリ：Tauri製 Windows 向けタスク管理アプリ
- 仕様バージョン：0.4（実装方針）
- 作成日：2026-10-14
- ステータス：実装済み

## 1. 目的

タスクの期限前に Windows デスクトップ通知を1回表示し、通知をクリックすると対象タスクを開けるようにする。

初期リリースでは、アプリのウィンドウを閉じてもプロセスを終了せず、タスクトレイに常駐して通知監視を継続する。アプリを完全終了した状態や PC の電源が切れている状態での通知は、初期リリースの対象外とする。

## 2. 基本方針

- 既存の SQLite データベースを継続利用する。
- 新しいデータベースは追加しない。
- 通知監視は React の画面内タイマーではなく、Tauri の Rust 側で実行する。
- Windows のデスクトップ通知を使用する。
- タスクトレイからウィンドウの再表示とアプリ終了を操作できるようにする。
- 将来的な Windows タスクスケジューラ連携を考慮し、通知の判定・状態管理と通知の実行方法を分離する。
- 以下の実装例は Tauri v2 を前提とする。実装前にプロジェクトの Tauri バージョン、既存プラグイン、SQLite アクセス方式を確認する。

## 3. 対象範囲

### 3.1 初期リリースの対象

- タスク単位のリマインダ有効／無効
- 期限の指定時間前に1回通知
- Windows デスクトップ通知
- 通知クリックによる対象タスクの表示
- タスクトレイへの常駐
- ×ボタン押下時のウィンドウ非表示
- トレイメニューからの再表示・明示的な終了
- SQLite による通知状態の永続化
- 完了・削除・期限変更時の通知予約の更新
- アプリ起動時の通知状態の再読み込み

### 3.2 初期リリースの対象外

- アプリ完全終了中の通知
- PC のシャットダウン中や電源オフ中の通知
- 複数端末間の通知同期
- 繰り返し通知・未完了時の再通知
- クラウド経由の Web Push

## 4. ユーザー仕様

### 4.1 通知設定

- タスクに期限日時（`due_at`）が設定されている場合、リマインダを有効化できる。`due_at` は期間フィールドとは独立した専用項目である。
- 通知タイミングは「期限の何分前か」で指定する。
- 初期値は期限の30分前とする。
- 期限がないタスクは通知対象外とする。
- 通知設定が無効なタスクは通知対象外とする。
- 通知タイミングの選択肢は、例として5分前、15分前、30分前、1時間前、1日前を用意する。実際の選択肢は UI 設計時に確定する。

### 4.2 通知ルール

- 通知はタスクごとに1回だけ行う。
- 通知予定時刻は `期限日時 - 通知までの分数` で計算する。
- 通知予定時刻がすでに過去の場合、初期仕様では遡って通知しない。
- 通知予定時刻にタスクが完了済み、削除済み、またはリマインダ無効の場合は通知しない。
- 通知済み状態は SQLite に永続化し、アプリ再起動後も同じ通知を繰り返さない。
- 期限変更時は通知予定時刻を再計算する。
- 完了・削除・リマインダ無効化時は未送信の通知をキャンセルする。
- 通知処理時には、タスクの最新状態を再確認する。
- OS の通知設定、スリープ、負荷等により表示が遅延または抑止される可能性があることを前提とする。

### 4.3 通知内容・クリック動作

通知には以下を表示する。

- タイトル：「タスクの期限が近づいています」
- 本文：タスク名

通知クリック時の動作：

1. アプリのウィンドウを表示する。
2. 最小化されていれば復元する。
3. 対象タスクの詳細画面を開く。
4. 対象タスクが削除済みなどで見つからない場合は、タスク一覧画面を表示する。

通知の表示と通知クリックイベントの受信は別機能として実装・テストする。採用する Tauri 通知 API がクリックイベントを提供するか確認し、必要に応じて Windows 通知アクティベーション連携を追加する。

## 5. ウィンドウとタスクトレイの動作

| 操作 | 期待動作 |
|---|---|
| アプリ起動 | メインウィンドウを表示し、通知監視を開始 |
| ウィンドウの × ボタン | ウィンドウを非表示にし、プロセスと通知監視を継続 |
| トレイの「開く」 | ウィンドウを表示・復元し、フォーカスする |
| トレイアイコンのクリック | ウィンドウ表示など、操作を割り当てる場合は別途仕様化 |
| トレイの「終了」 | アプリプロセスを終了し、通知監視を停止 |
| アプリ再起動 | SQLite から通知状態を読み込み、監視を再開 |
| Windows 再起動後 | アプリ自動起動を設定している場合に限り、起動後に監視を再開 |

初期リリースでは、ウィンドウの非表示とアプリ終了を明確に区別する。OS 終了やプロセス強制終了時は通知監視が停止する。

## 6. 技術構成

| 領域 | 役割 |
|---|---|
| React / TypeScript | タスク UI、リマインダ設定 |
| Tauri / Rust | ウィンドウ制御、トレイ、通知監視 |
| 既存 SQLite | タスクと通知状態の保存 |
| Tauri Notification Plugin | Windows 通知の表示 |
| Tauri Tray API | タスクトレイアイコンとメニュー |
| Rust の非同期タスク等 | 定期的な通知対象の確認 |

監視処理を React コンポーネントのタイマーに依存させない。通知監視は Rust 側で実行し、ウィンドウ非表示後も継続させる。

## 7. データ設計

既存の SQLite スキーマを先に確認し、同等のカラムがあれば再利用する。以下は論理的なフィールド案であり、実テーブル名・カラム名は既存スキーマに合わせる。

### 7.1 タスク側のフィールド

既存の期間フィールド（`scheduled_date` / `end_date` / `end_time`）とは独立した期限日時を追加する。通知時刻は `due_at` のみを起点とする。

| フィールド | 意味 |
|---|---|
| `due_at` | 期限日時（UTC ISO）。未設定なら通知対象外 |
| `reminder_enabled` | リマインダ有効／無効（初期値はオフ） |
| `reminder_lead_minutes` | 期限の何分前に通知するか（初期値 30） |
| `reminder_sent_at` | 通知成功日時。未通知なら NULL |

`due_at` 変更時は `reminder_sent_at` を NULL に戻し、新しい予定で再通知できるようにする。

### 7.2 通知専用テーブルを採用する場合

1タスクにつき1回の通知だけならタスクテーブルへのカラム追加で足りる可能性がある。複数種類の通知、履歴、再通知等を将来扱う場合は、通知専用テーブルを検討する。

| フィールド | 意味 |
|---|---|
| `id` | 通知 ID |
| `task_id` | 対象タスク ID |
| `scheduled_at` | 通知予定日時 |
| `status` | `pending` / `sent` / `cancelled` / `failed` |
| `schedule_version` | 期限変更時の古い予約を無効化する世代番号 |
| `sent_at` | 通知処理日時 |
| `created_at` | 作成日時 |

同一タスクの重複予約を防ぐ制約や、通知処理の排他制御を実装する。通知表示と DB 更新は OS をまたぐため、完全な原子性を保証できない点を考慮し、再起動時の重複・取りこぼしポリシーを定義する。

### 7.3 日時

- DB にはタイムゾーンの扱いを統一して日時を保存する。
- 推奨は UTC 保存、表示時にローカル時刻へ変換する方式。
- 既存 DB がローカル時刻で保存している場合は、既存形式を無条件に変更せず、移行方針を決める。

## 8. 通知監視の処理

通知対象の確認は60秒間隔。監視間隔は定数として変更できる構造にしておく。

1. 現在時刻を取得する。
2. 通知予定時刻を過ぎた未通知タスクを取得する。
3. タスクの存在、期限、完了状態、リマインダ有効状態を再確認する。
4. 通知予定時刻が未来、または対象外になった場合は処理をスキップする。
5. 通知対象であれば Windows 通知を表示する。
6. 通知状態を SQLite に保存する。
7. 次回の監視まで待機する。

通知時刻の式：

`通知予定日時 = 期限日時 - reminder_lead_minutes`

通知の検出遅延は、通常は監視間隔以内を目標とする。ただし OS 負荷やスリープ等による遅延はあり得る。

### 重複通知対策

- 通知済み状態を SQLite に保存する。
- 同一通知を複数の監視処理が同時に処理しないようにする。
- 通知処理時に最新のタスク状態を再確認する。
- 期限変更時は予約の世代番号を更新するか、通知状態を適切にリセットする。
- DB 更新と OS 通知表示は単一トランザクションで完全に原子化できないため、失敗時の再試行方針を明確にする。

## 9. 実装手順

### Step 1：既存構成を確認

- Tauri のバージョン（v1 / v2）
- `tauri::Builder` を構築している Rust ファイル
- SQLite のアクセス方式（`rusqlite`、`sqlx`、Tauri SQLite プラグイン等）
- タスクテーブルの実名とカラム
- メインウィンドウのラベル（例：`main`）
- 既存のプラグイン・コマンド登録

### Step 2：トレイ機能を追加

- Tauri v2 の Tray API を利用してトレイアイコンを作成。
- 「開く」「終了」メニューを追加。
- 「開く」でメインウィンドウを表示・復元・フォーカス。
- 「終了」でアプリを明示的に終了。

### Step 3：×ボタンを非表示動作に変更

- ウィンドウの CloseRequested イベントを受信。
- イベントの既定終了処理をキャンセル。
- メインウィンドウを非表示にする。
- トレイの「開く」から再表示できることを確認。

### Step 4：通知プラグインを登録

- Tauri v2 の Notification Plugin を追加。
- Rust 側でプラグインを登録。
- Windows で通知許可やインストール版の挙動を確認。
- 通知表示とクリックイベントを分けて実装する。

### Step 5：通知監視を Rust 側に追加

- 非同期タスク等で監視を実行。
- 既存 SQLite のアクセス層を再利用。
- React のウィンドウが非表示でも監視を継続。
- アプリ終了時には監視処理を停止する。

### Step 6：通知状態を永続化

- 既存スキーマを確認し、必要最小限の変更を加える。
- 期限変更・完了・削除・通知無効化時に予約を更新・キャンセル。
- 再起動後に通知状態を復元する。

### Step 7：クリックで対象タスクを開く

- 通知にタスク ID を関連付ける。
- 通知クリックイベントを受け取る。
- メインウィンドウを表示して対象タスクの詳細画面へ遷移。
- 対象が存在しない場合は一覧画面を表示。

## 10. 受け入れテスト

- [ ] トレイアイコンが表示される。
- [ ] ×ボタンでウィンドウが非表示になり、プロセスが継続する。
- [ ] トレイの「開く」でウィンドウを再表示できる。
- [ ] トレイの「終了」でアプリプロセスが終了する。
- [ ] 期限前に通知が1回表示される。
- [ ] 通知済みのタスクについて重複通知されない。
- [ ] 通知前にタスクを完了すると通知されない。
- [ ] タスク削除後に通知されない。
- [ ] 期限変更後、古い通知予定時刻では通知されない。
- [ ] リマインダ無効化後に通知されない。
- [ ] 通知クリックで対象タスクが開く。
- [ ] アプリ再起動後に通知状態が復元される。
- [ ] Windows の通知が無効な場合、適切な案内が表示される。
- [ ] PC のスリープ中に通知時刻を過ぎた場合、復帰後に古い通知を一斉送信しない。
- [ ] アプリ完全終了中は初期仕様では通知されない。

## 11. 将来拡張：完全終了中の通知

初期リリースの安定後、Windows タスクスケジューラ等から通知処理を起動する方式を検討する。

将来拡張でも通知ルールと SQLite の状態管理を再利用できるように、通知対象の判定ロジックを UI や通知 API から分離する。

完全終了中の通知は、Windows のログオン状態、PC のスリープ、アプリのインストール方式、通知のアクティベーション方法などを含めて別途設計・検証する。

## 12. 確定した実装方針（旧・未確定事項）

- Tauri v2.11。SQLite は sqlx カスタムコマンド（`AppDb`）。専用通知テーブルは作らない。
- 期限の起点は新しい `due_at`。期間フィールドとは自動同期しない。
- リマインダはオプトイン。有効化時のリードは 30 分。
- `due_at` 変更時は `reminder_sent_at` をリセットする。
- 予定時刻から 2 分を超えていれば送らない（起動遅れ・スリープ復帰の一斉送信を防ぐ）。
- トレイ左クリックは「開く」と同じ（表示・復元・フォーカス）。
- Windows 自動起動は初期リリースに含めない。
- 通知クリックは extra の `task_id` と `open-task` イベントでフロントへ渡す。
- OS 通知が失敗したら `reminder_sent_at` は更新せず、次ポーリングで再試行する。2 分ウィンドウを過ぎたら打ち切り。
